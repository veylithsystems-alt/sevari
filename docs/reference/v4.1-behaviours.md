# Behaviours extracted from Sevari BDI v3.6.0 / v4.1.0 (n8n)

Contract §2: the n8n builds are a **behavioural reference only**. No code is copied. Every behaviour kept becomes a test; every defect found becomes a regression test that the new build must pass.

Sources (committed read-only under `docs/reference/raw/`):
- `BDI_Sevari_v3.6.0.n8n.json`: 581 nodes. This is the version the contract names.
- `sevari_bdi_v4.1.0_flagship.n8n.json`: 582 nodes, the latest. It differs from v3.6 in 13 nodes (cron throttles, schedule-trigger fixes) plus one added node, `SVR:SENTINEL:Call`. The behaviour below is the same for both unless noted.
- `v4.1-node-index.txt`: every node with its type, webhook path, schedule or SQL prefix.

Status key: **KEEP** (behaviour carried forward, with the test that proves it), **CHANGE** (kept in spirit, done differently, with the reason), **DEFECT** (bug in the reference, with the regression test the new build must pass).

## 2. Guardian (threat screen)

`GRD:Scan`: four regex families (prompt injection, exfiltration, script injection, "sensitive extraction"), behavioural signals (burst, high-frequency sender), a **decay factor of 0.7 for senders with 10 or more prior safe messages**, then pass / flag (>20) / escalate (>40) / quarantine (>75). Repeat high-threat senders go on a one-hour blocklist.

| Behaviour | New build | Status |
|---|---|---|
| Customer text is treated as hostile input | Same, and stronger: the model has no tools and no database, output is schema-constrained and grounded (§36.3, F36) | KEEP |
| Score thresholds pass/flag/escalate/quarantine | Kept as the input screen, but **the screen never decides a send**. Grounding and the autonomy policy do. | KEEP |
| Decay factor for "trusted" senders | **Removed.** An attacker can send ten harmless messages and then inject at 70% strength. | DEFECT D-2 |
| Product brief claims "11 threat categories"; the code has 4 regex families plus 2 behavioural signals | Claims register (§43): no claim unless it's measured | DEFECT D-3 (claim, not code) |

Clarifying questions in the reference were written for an IT-support tenant (`Device or hardware fault`, `Network and connectivity`...). The new build moves them into each vertical pack.

## 4. Generation tiers (failsafe)

T0 desktop GPU (Cloudflare Tunnel), T1 Mistral 7B (90s), T2 Llama 3.2 3B (60s), T3 Gemma 2 2B (45s), T4 Phi-3 Mini (30s), T5 templates (<10ms, cannot fail), T6 human. SENTINEL marks VPS2 down and the pipeline skips to T5.

| Behaviour | New build | Status |
|---|---|---|
| A guaranteed response path that needs only the database (T5) | The ACK is deterministic and never touches inference (§5.2, F7). Templates are the default for routine intents (§5.3) | KEEP |
| T6 human with a waiting queue | UNKNOWN as a state (§5.4), owner escalation with the facts gathered | KEEP |
| T1–T4 sequential fallback with long timeouts | Model registry (§9): best active model meeting the latency budget; the degradation ladder (§36.2) | CHANGE |
| **T0: a home desktop GPU reached through Cloudflare Tunnel** | Not carried forward without a decision: Cloudflare becomes a processor on the path of customer data, and the desktop is infrastructure off the processor register (INV-3, §26) | **QUESTION for Dan** (Q-3 in `docs/QUESTIONS_FOR_DAN.md`) |
| `WRK:DeadlineForceT5`: an overdue enquiry gets a template with `approval_required: false` | The ACK path is always automatic (§7.2: `ack` class). Anything beyond an ACK still goes through the autonomy policy | KEEP (ACK only) |

## 7. Audit trail

| n8n | Behaviour | New build | Status |
|---|---|---|---|
| `OUT:PG:Audit` and others | `prev_hash` = last row's hash; **`row_hash = sha256(enquiry_id || now())`** | Hash computed **in the database** over `prev_hash` and the full canonical row, per-tenant chain, serialised appends, signed checkpoints (T-AUD) | DEFECT D-13 (critical) |
| `SENTINEL:AuditVerify` hourly | Reads the last 1000 rows | `sevari_meta.audit_verify()` checks every link and recomputes every hash; signed checkpoints catch a full rewrite | KEEP / CHANGE |

D-13 matters most: because the stored hash covers only the enquiry id and a timestamp, **anyone can change the content of any audit row and the chain still verifies.** The "tamper-proof seal" in the product brief did not hold. The new chain is proven by `tests/phase1/t-aud-audit-chain.test.ts`, which tampers as a superuser and also rewrites the whole chain.

## 8. Personal data and erasure

| n8n | Behaviour | New build | Status |
|---|---|---|---|
| `SEC:EncryptPII` | AES-256-GCM with a per-tenant DEK wrapped by a master key | Envelope encryption kept, plus AAD binding each ciphertext to tenant, region, table, column and row (I12) | KEEP / CHANGE |
| `SEC:EncryptPII` `encrypt()` | **If the key is missing, returns the plaintext**; on error stores the literal `[ENCRYPT_ERROR]` (data loss) | Fails closed: no key = boot refused (INV-9); encryption errors abort the transaction | DEFECT D-14 |
| `sender_email_hash` | Unkeyed SHA-256 of the email | Keyed HMAC blind index per tenant, destroyed by crypto-shred. An unkeyed hash of an email can be reversed by guessing likely emails | DEFECT D-15 |
| `GDPR:ErasureExecute` | `'ERASED-' + encode(...)` uses `+` on text, which is a PostgreSQL type error, so **the erasure statement fails**. It also leaves messages, approvals, audit payloads and the SMS log untouched | Registry-driven erasure (§6.4, F5), crypto-shred, certificate | DEFECT D-16 |
