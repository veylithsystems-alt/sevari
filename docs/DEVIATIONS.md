# Deviations from the build contract (§13.3)

Every difference from `docs/BUILD_CONTRACT.md` (v1.11), with what, why, risk and proposal. Nothing here is a quiet workaround.

| ID | What | Why | Risk | Proposal |
|---|---|---|---|---|
| DEV-001 | Work is pushed to the branch `claude/sevari-core-build` as one commit per phase, not one PR per phase (§0.3, §11) | Dan's instruction in this session ("Just push to a branch") | Phases are reviewed together, not one at a time | Dan can ask for a PR per phase at any time; each phase is a separate commit, so they split cleanly |
| DEV-002 | Contract tests for phases not yet delivered are **skipped in the CI gate** and **red in the full run** (`pnpm test:all`, CI job `contract-progress`) | §11 Phase 0 wants every test written red, and §3 wants CI to block on regressions. Both can't hold on day one: a red-by-design test would block every merge | A real regression in an undelivered phase isn't caught by the gate. Mitigation: once a phase is in `tests/contract/phases.json`, its tests are gated | Keep. Phases are added to the delivered list only when their exit criteria are green |
| DEV-003 | T1–T23 are placeholders | The v3.6 resurrection review (§2) wasn't supplied | Behaviours it covers may be missed | Supply the review, or accept defects D-1 … D-16 as the mapping (CONTRACT_REVIEW R-3) |
| DEV-004 | Local test runs use a native PostgreSQL 16 when Docker isn't available (`SEVARI_TEST_DATABASE_URL`); CI uses a Postgres 16 service container rather than Testcontainers | Docker Hub rate-limited this environment. A CI service container gives the same isolation more simply | None for correctness: each test run creates and drops its own database, and schema-altering tests get a fresh one | Keep both paths; Testcontainers is still used automatically when Docker works and no URL is set |
| DEV-005 | Appendix 2 (pilot pricing and outreach) is missing from the contract file, which is also truncated | Source file is incomplete (CONTRACT_REVIEW R-1) | The §46 scorecard fields and end-of-pilot questions can't match Appendix 2 exactly | Built as data with placeholder fields until Appendix 2 is supplied |
| DEV-006 | `schema_migrations` uses `version_no` (not `version`) for its row-version column | `version` is the migration number, a natural primary key | None | Keep; the schema lint knows this one exception |
| DEV-007 | The job queue is a small in-repo Postgres queue (`packages/db/src/queue.ts`), not `graphile-worker` or `pg-boss` (§4) | Both libraries keep their jobs in their own tables outside the tenant model (no `tenant_id`/`region` columns, no RLS). The in-repo queue lives under the same RLS rules, carries ids only, and is shaped for the Temporal-ready port (ADR-0002). It is about 150 lines, with no new dependency | We maintain queue code ourselves (leases, retries, dead-lettering) | Keep; revisit when moving to Temporal |
| DEV-008 | The ACK step runs a deterministic screen first (STOP, risk to life, always-human list) before choosing the template (§5.2 lists ACK before normalise and intent) | Without it, a customer who texts STOP would get an acknowledgement, and a risk-to-life message would get a generic one before the safety message. The screen is pure, takes milliseconds and never touches inference, so the ACK target (F7) is unaffected | None found: F7 p95 0.49s with the CPU saturated | Keep; propose wording for §5.2: "ACK (deterministic, after a deterministic opt-out and safety screen)" |
| DEV-009 | The holdout corpus `eval/holdout/starter.jsonl` was written by the builder, and the builder has seen its results (Part J §68 requires independence) | No independent cases have been supplied yet. The harness, the isolation guard and the format are real; the content is a placeholder | F3H passing is weak evidence until humans supply the cases | Dan or a reviewer writes the holdout cases before any release (Q-13) |
| DEV-010 | Phase 5 is delivered as code with the benchmark harness, but its exit evidence ("model benchmark table on target box", §11) is not yet recorded: `eval/models/BENCHMARK.md` is empty | The build environment has no model server and no network; a benchmark here would measure the wrong machine | None for safety: with no promoted model the system runs rules and templates only (every test proves the model-off path). Model quality is unmeasured until the run | Dan (or whoever operates the VPS) runs `docs/ops/model-benchmark.md`; the table is committed; readiness item MB-1 records it |
| DEV-011 | Grounding no longer lets a customer's own **prices, percentages, bare numbers or links** support a claim; only their postcode, phone, email, dates and times may be echoed (§10.1 F3 says values in "the enquiry" may be echoed) | Building the injection set showed the gap: "quote me £10" would have let a reply say "£10". Echoing a customer's money back reads as agreeing a price | Some harmless echoes ("your 2 toilets") now block and fall back to the template | Keep; propose F3 wording: "…not in the bundle, or (for contact details, dates and times only) in the enquiry" |
| DEV-012 | The model registry is administered with an owner-role script (`scripts/model-registry.ts`); promotions are recorded on the registry row (approver, time, benchmark file) rather than in a tenant audit chain | The registry is cell configuration with no tenant, and the audit chain is per tenant. A cell-level audit chain arrives with the operator console (Part C) | A promotion is visible in the row and in git (the committed benchmark file), but not hash-chained | Add a cell audit chain when the operator console is built, and record promotions there |
| DEV-013 | Owner and team sign-in uses high-entropy bearer tokens (stored as SHA-256, 30-day expiry), not passkeys yet (R-12) | The approval, authority and acknowledgement rules (Phase 18) needed a credential to bind to; passkeys need the owner app's browser flow, which comes with the owner UI | A stolen token works until it expires or is revoked. Mitigations: per-user, per-tenant tokens; revocable; operator tokens are a separate kind that can never act for a business (F58) | Passkeys (WebAuthn) for owner sign-in before the first pilot; bearer tokens kept only for machine-to-machine use |
| DEV-014 | Branch coverage (≥95% on domain, grounding, approvals, autonomy, privacy) and mutation testing (Stryker ≥80% on grounding and approvals) are not yet measured in CI (§10.1) | Both need new dev dependencies (`@vitest/coverage-v8`, Stryker), which need an ADR line (§12) | Untested branches could hide defects in safety-critical packages. Mitigation: every contract test for these packages is written to attack the rule, not just call it | ADR for the two tools, then a CI job that fails below the thresholds. **Missed its first target (Phase 8 closed without it); new target: before the stress-test campaign (readiness ST-1)** |
| DEV-015 | Model wording (Phase 5) is wired as a library, but no tenant can switch it on yet: replies are always templates | Switching it on is a per-tenant, per-message-type setting, which belongs on the owner settings screen (Phase 11) | None for safety (templates are the contract's default, §5.3) | Add the setting with onboarding (Phase 11); it stays off by default |
| DEV-016 | Phase 9's exit ("both lifecycles run on the engine with the house tenant", §25) is proven by new contract tests T-LC-1–4 and T-BOOK-1–3, added to the registry because §25 names no test ids. Bookings use one bookable resource per business (`resource = 'default'`) | Adding tests is free (registry rule); multi-team scheduling needs the owner to say which jobs need which engineer or van, which belongs with onboarding (Phase 11) and calendar integration (Part M) | A business with two teams can only take one job at a time through Sevari until then; it can never be double-booked | Add resources (teams, vans, chairs) to onboarding and the calendar integration; the database rule already works per resource (T-BOOK-1) |
| DEV-017 | The F2 static scan now skips the evidence links in `config/processors.yaml` (`url`, `list_url`, `terms_url`, `source`): the provider's terms and DPA pages | They are citations the registry schema requires (§69 "record your sources"), not hosts Sevari connects to. Every other URL in code and config is still scanned, and the processor's real API host must be on the allowlist | A host named only in a citation line would not be flagged. Mitigation: the egress client still refuses any host not on the allowlist at run time | Keep; propose F2 wording: "…every URL host in source and config, other than cited evidence, is allowlisted…" |
| DEV-018 | Suppression is per business, not yet cell-wide across businesses (§17.2: "honoured across tenants where the person opted out of the sender class") | Each business's contacts are blind-indexed with that business's own key, so the same address can't be matched across businesses without a cell-wide index key, and no sender class spans businesses yet: every message today comes from one business, and marketing is consent-only per business | A person who opts out of one business's messages can still get service replies from another business they contact. That is expected, because they wrote to that one | Add a cell-level suppression ledger (keyed with a cell index key in the KMS) before any cross-business sender class exists (Veylith's own marketing, VANGUARD, Tier C campaigns) |
| DEV-019 | Phase 12 is delivered against a fake payment processor: no real processor adapter and no payment-webhook HTTP route yet. Invoices go out without a payment link until a processor is connected | A real processor is a new supplier, so it needs an ADR, Dan's approval and an allowlist entry (§29, §69), and each business connects its own account (Mode 1). Q-24 asks which one | Customers can't pay by link until then; they pay as they do today. Everything else (ledger, invoices, reconciliation, chasing) is real | ADR for the chosen processor, its adapter behind `PaymentProcessor`, a signed-webhook route per business, then live tests against its sandbox |
| DEV-020 | Payment reminders use a default schedule (1, 7 and 14 days after the due date; at most three) rather than one each owner sets (§19.2) | The owner settings screen comes with the owner app work | Every reminder still needs the owner's approval, and the contact rules still cap and delay them | Owner chasing settings (intervals, tone, cap) in the settings screen |
| DEV-021 | Phase 13 is delivered with accounting sync proven against a fake provider; no Xero, QuickBooks or FreeAgent adapter yet (§19.5 names them first). Plans are in `config/plans.yaml` as proposed figures, not approved | Each accounting platform is a new supplier needing an ADR, Dan's approval and its own API terms checked (§19.5: "which I haven't verified"). Prices await Q-2 | Businesses can't sync to their books until an adapter is approved; Sevari can't bill until Dan approves the plan figures with `scripts/approve-plans.ts` | ADRs for Xero, then QuickBooks and FreeAgent, each an adapter behind `AccountingPort`; Dan answers Q-2 and runs the approval script |
| DEV-022 | Complaint remedies: a refund or credit is offered in a message the owner approves, but the money itself moves through the business's own payment provider and is recorded when the provider reports it; Lifecycle V SLA credits (§20.7) use the same workflow without automatic credit calculation yet | The refund is a payment-provider action (Q-24 not yet decided), and SLA terms come with the Veylith contract pack | The owner refunds in their provider's dashboard for now; Sevari records it from the provider's event | Refund through the money port once a processor is approved; SLA credit rules as data once the SLA terms are set |
| DEV-023 | Handing a case to an outside party (§21.3): approval seals exactly the approved fields into an encrypted bundle, but the owner sends it to the recipient themselves; Sevari doesn't transmit it yet. Capacity referral to a partner business (customer consent, off by default) isn't built | Sending to a partner automatically means connecting to that partner's systems, and each new host needs an allowlist entry and an approved supplier (§29, §69). Capacity referral is optional and off by default in the contract | The owner does one manual step (forward the approved details). Nothing can be shared without the approval, and the bundle has only the fields approved | Add delivery by email through Brevo to the partner's registered address (no new supplier needed) with the owner app work; capacity referral with Part M growth |
| DEV-024 | The customer portal (§22) shows bookings and invoices and has one-click "stop marketing" and "stop all messages". Rescheduling from the portal, sending the link automatically in messages, and the automatic accessibility test (axe in CI, WCAG 2.2 AA) are not built yet | Rescheduling needs the owner's approval flow on the page; the link goes into templates with the owner app work; axe is a new dev dependency that needs an ADR line (§12), like DEV-014 | Customers get the link only when the owner issues it; accessibility is unmeasured. The page is plain HTML with no scripts, which keeps it simple for screen readers | Add reschedule requests (owner approves), the link in booking and invoice templates, and axe with the coverage tools ADR before the stress-test campaign |
| DEV-025 | Business offboarding uses a 30-day notice and a 30-day grace period (§21.1 says "a notice per the contract") | Veylith's terms with businesses aren't written yet | If the terms say something else, the code is out of step until changed | Two constants in `packages/privacy/src/offboarding.ts`, to become region data once Dan answers Q-25 |
| DEV-026 | Owners sign in with single-use email links (15 minutes), not passkeys yet (R-12, R-13 make passkeys primary and links the fallback) | Passkeys need a WebAuthn library (a new dependency, so an ADR line under §12) and the browser flow in the owner app | An attacker who controls someone's mailbox can sign in as them. Mitigations: links are single use, expire in 15 minutes, are stored only as hashes, and a few at most are sent per address an hour; sessions can be ended at once | Passkeys with the WebAuthn ADR before the first pilot; email links stay as the fallback (R-13) |
| DEV-027 | Self-serve sign-up is built but closed: it opens only when the cell is configured with the version and links of Veylith's published customer terms and privacy notice | Those documents need counsel (readiness items); signing people up to terms that don't exist would be misleading | Nobody can sign up until then; existing accounts can still sign in | Dan publishes the terms and privacy notice, then sets their version and links in the cell's settings (Q-26) |
